## 1. Что требует GDD (и только это)

| Требование | GDD |
|---|---|
| У игрока есть инвентарь с предметами | §5.2 |
| После смерти предметы из инвентаря остаются на месте смерти в контейнере с добычей | §5.2 |
| Игрок может вернуться и забрать вещи | §5.2 |
| Новый игрок / игрок без точек возрождения появляется в случайной точке карты | §4.4, §5.3 |
| Спальники и кровати создаются крафтом и служат точками возрождения | §5.3, §6.2 — **Этап 3**, здесь только задел |

Для смерти нужен хотя бы показатель здоровья. В GDD перечень показателей — открытый вопрос №1, поэтому предлагаю **только здоровье** как минимально необходимое (см. вопрос В7). Голод, жажда, температура — не трогаем.

## 2. Технические решения (рекомендации)

### Т1. Описание типов предметов

| Вариант | Плюсы | Минусы |
|---|---|---|
| **А. `UPrimaryDataAsset` на каждый тип** (`URoxiItemDefinition`) | Стандарт UE5, загрузка по ID через Asset Manager, ссылки на иконку/меш без загрузки в память, легко расширять полями | Неудобно массово править баланс |
| Б. `DataTable` (таблица, импорт из CSV/Excel) | Удобно для баланса сотен предметов | Хуже расширяется под разные виды предметов (оружие, еда, постройки) |

**Рекомендация: А.** Баланс-таблицу при необходимости можно добавить позже поверх ассетов.

Поля на старте — только необходимые: ID, название, описание, иконка, меш для выброшенного предмета, максимальный размер стопки. Остальное (категории, прочность, вес) — по решению вопросов ниже.

### Т2. Экземпляр предмета

| Вариант | Плюсы | Минусы |
|---|---|---|
| **А. Структура** `FRoxiItemStack { ItemId, Quantity, ... }` | Дёшево по памяти и сети, тривиально сохраняется (Р4), подходит под «экономнее по ресурсам» | Уникальное поведение предмета — через его определение, а не через собственный класс |
| Б. `UObject` на каждый предмет (подход Lyra) | Гибко | Тысячи UObject на сервере, дороже репликация и сохранение |

**Рекомендация: А.**

### Т3. Контейнер — один компонент для всего

`URoxiInventoryComponent` (компонент актора): массив слотов, каждый слот — `FRoxiItemStack` или пусто. Один и тот же компонент используется для:
- инвентаря игрока;
- контейнера с добычей после смерти (§5.2);
- в будущем — ящиков, верстаков, торговцев (не делаем сейчас).

Сетевая передача — `FFastArraySerializer`: по сети уходят только изменившиеся слоты.

### Т4. Кто видит содержимое контейнера

| Контейнер | Кому реплицируется |
|---|---|
| Инвентарь игрока | **Только владельцу** (`COND_OwnerOnly`) |
| Контейнер в мире (добыча, позже ящики) | **Только тем, кто его сейчас открыл** — как в Rust |

Для контейнеров в мире есть два способа:
- **А. Как в Rust:** сервер отправляет содержимое только игрокам, которые открыли контейнер, и рассылает им изменения, пока контейнер открыт. Чит «видеть содержимое ящиков сквозь стены» невозможен — данных у клиента нет.
- Б. Реплицировать содержимое всем, кто рядом. Проще, но любой клиент знает, что лежит во всех ближних ящиках.

**Рекомендация: А.**

### Т5. Операции — только на сервере (Р1)

Клиент отправляет намерение (серверный RPC через `ARoxiPlayerController`), сервер проверяет и выполняет:
- переместить / объединить / разделить стопку (в т.ч. между инвентарём и открытым контейнером);
- выбросить предмет на землю;
- поднять предмет с земли;
- открыть / закрыть контейнер.

Проверки сервера: существует ли предмет и количество, принадлежит ли контейнер игроку или открыт ли им, дистанция до контейнера/предмета, жив ли игрок.

### Т6. Предметы в мире

`ARoxiWorldItem` — актор с одной стопкой, лежит на земле, поднимается взаимодействием. Неподвижен большую часть времени → «спящий» по сети (Dormancy), почти не стоит ресурсов.

### Т7. Смерть и контейнер с добычей (§5.2)

1. Здоровье ≤ 0 → сервер помечает персонажа мёртвым.
2. Сервер создаёт `ARoxiLootContainer` (актор + `URoxiInventoryComponent`) на месте смерти и **переносит в него все предметы** игрока.
3. Персонаж удаляется; игроку показывается экран возрождения (§5.3).
4. Контейнер может открыть любой игрок (кто именно — вопрос В5).

Тело/модель контейнера на старте — простая заглушка (мешок/ящик); визуал — отдельно.

### Т8. Появление в случайной точке (§4.4)

**Рекомендация:** заранее расставленные на карте точки появления (`ARoxiSpawnPoint`), сервер выбирает случайную свободную. Полностью случайная точка на ландшафте рискованна: можно появиться в воде, внутри постройки, в зоне POI. Правила (открытый вопрос №3) — см. В6.

Задел под спальники/кровати: выбор точки возрождения устроен так, что Этап 3 просто добавит новый тип точки.

### Т9. Отладка

Без UI игру не проверить, а дизайн интерфейса не определён. Предлагаю **временный отладочный интерфейс** (простой виджет-список + консольные команды `roxi.Give <Item> <N>`, `roxi.Kill`) — только для разработки, вырезается из Shipping. Финальный UI — отдельная задача после утверждения дизайна.

### Т10. Тестовые предметы

Для проверки нужны 2–3 предмета. Предлагаю нейтральные заглушки без игрового смысла: `DEV_TestItemA` (стопка 100), `DEV_TestItemB` (стопка 1). Реальные предметы — после утверждения списка ресурсов (открытый вопрос №8).

## 3. Открытые вопросы (игровой дизайн — решает разработчик)

Для каждого — вариант «как в Rust», раз сеть делаем по образцу Rust.

| № | Вопрос | Как в Rust | Если не решено сейчас |
|---|---|---|---|
| В1 | Структура инвентаря | 24 слота основного инвентаря + 6 слотов пояса (быстрый доступ) + 7 слотов одежды | Делаю настраиваемые размеры, по умолчанию 24 + 6 |
| В2 | Размер стопок | Свой у каждого предмета (дерево — 1000, камень — 1000 и т.д.) | Поле в определении предмета |
| В3 | Прочность предметов | Есть у инструментов, оружия, одежды | Не делаю сейчас; добавляется полем позже |
| В4 | Вес / ограничение переносимого | Нет, только слоты | Не делаю |
| В5 | Кто может забрать добычу после смерти | Любой игрок | Любой игрок |
| В6 | Правила случайного появления | Случайная точка на побережье | Случайная из расставленных точек |
| В7 | Здоровье | 100 HP | Только здоровье, 100 единиц; урон — только отладочной командой |
| В8 | Теряются ли надетые вещи и пояс при смерти | Да, всё | Всё, что у игрока есть |
| В9 | Время жизни контейнера с добычей (откр. вопрос №4) | Несколько минут | Без ограничения до решения |

## 4. План реализации Этапа 2 (после согласования)

1. Определения предметов (Т1), стопки (Т2), компонент инвентаря (Т3) с репликацией владельцу (Т4).
2. Серверные операции (Т5) + отладочные команды и временный UI (Т9) + тестовые предметы (Т10).
3. Предметы в мире: выбросить / поднять (Т6).
4. Здоровье, смерть, контейнер с добычей, открытие контейнера с репликацией «как в Rust» (Т4, Т7).
5. Точки появления и экран возрождения (Т8).
6. Проверка на Listen Server с 2 клиентами по каждому пункту; замер нагрузки на стенде (сотни выброшенных предметов и контейнеров).

Каждый пункт — отдельный коммит.
