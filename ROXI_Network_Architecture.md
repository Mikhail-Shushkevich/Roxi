## 1. Нагрузочный профиль

Сервер одновременно держит: до 100 игроков, тысячи элементов построек, выпавшие предметы и контейнеры, ресурсные узлы, NPC, животных, заражённых, транспорт, погоду — на карте ~4×4 км. Главный ограничитель — CPU сервера на репликации: проверка «каждый объект × каждое подключение».

## 2. Решения

### Р1. Модель авторитетности — ✅ как в Rust

**Как в Rust:**
- Сервер — единственный источник истины для инвентаря, крафта, строительства, здоровья и урона, лута, контейнеров. Клиент шлёт только намерения («скрафтить», «поставить стену», «открыть ящик»), сервер проверяет и выполняет.
- **Попадания** определяет клиент и сообщает серверу; сервер проверяет правдоподобие (дистанция, линия видимости, баллистика, скорострельность) и только потом применяет урон.
- **Движение** — клиент сообщает позицию, сервер проверяет (скорость, полёт, прохождение сквозь стены) и откатывает нарушителя.

**Реализация в UE:**
- Инвентарь/крафт/строительство/урон — серверная логика, RPC `Server...` с проверками. Без отличий от Rust.
- Попадания — клиент сообщает, сервер валидирует. Без отличий от Rust. (Реализуется вместе с оружием, не на Этапе 1.)
- ✅ **Движение — встроенная модель UE (отличие от Rust, решение 0.3).** В UE есть готовый `CharacterMovementComponent`: клиент предсказывает движение, сервер его пересчитывает и при расхождении поправляет клиента. Для игрока это ощущается так же, как в Rust, но защита от speed/fly-хаков встроена, а не пишется вручную. Сделать «как в Rust» (сервер принимает позицию клиента) тоже можно, но это отключение встроенной защиты и ручная античит-проверка. **Рекомендация: встроенная модель UE.**

### Р2. Система репликации — ✅ принцип как в Rust

**Как в Rust:** мир поделён на сетку ячеек («network groups»). Игрок получает данные только об объектах в своей и соседних ячейках; дальние объекты ему вообще не отправляются.

**Реализация в UE:** прямой аналог — пространственная сетка **Replication Graph** (или пространственный фильтр Iris).
- Этап 1: стандартная репликация + **Push Model** + дистанции и Dormancy (быстрый старт, код совместим с обоими вариантами).
- Конец Этапа 1: включаем сетку Replication Graph и сравниваем на нагрузочном стенде. Iris как альтернативу оцениваем там же.

### Р3. Массовые объекты мира — ✅ логика как в Rust, ❓ техническая форма

**Как в Rust:** каждый элемент постройки (фундамент, стена, дверь, ящик) — самостоятельный сетевой объект со своим здоровьем, уровнем материала, улучшением и разрушением. Работает благодаря сетке из Р2: игрок получает только ближние объекты.

**Реализация в UE:**
- Игровая логика — 1:1 как в Rust: каждый элемент независим (своё HP, материал, улучшение, разрушение).
- ❓ **Техническая форма — риск.** Актор в UE тяжелее объекта Rust по памяти и стоимости обработки. «Один актор на элемент» + сетка Replication Graph может хватить, а может нет — на тысячах элементов это надо проверить. Предложение: начать с «один актор на элемент» (как в Rust), на Этапе 3 замерить, и при нехватке перейти к варианту «актор-база с массивом элементов» — **логика для игрока при этом не меняется**. Решение о переходе — на ваше согласование по результатам замеров.
- Ресурсные узлы, ИИ — решаются при проектировании соответствующих систем (GDD пока не определяет).

### Р4. Хранение данных — ✅ как в Rust

**Как в Rust:** состояние мира целиком хранится на самом игровом сервере в файле сохранения, который периодически записывается (каждые несколько минут) и при выключении сервера; отдельные данные игроков — в локальной базе SQLite на сервере. Внешней центральной базы нет.

**Реализация в UE:**
- Состояние мира (постройки, контейнеры, спальники, предметы на земле, инвентари игроков) — сохраняется **на сервере**: периодический снимок + сохранение при остановке. Формат (`USaveGame` или SQLite — плагин `SQLiteCore` есть в движке) выберу при реализации, это внутренняя деталь без влияния на игру; вынесу на согласование вместе с кодом.
- Вайпов пока нет → мир хранится бессрочно.
- Постоянный профиль (уровень, достижения — GDD §13): пока хранится там же, на сервере, отдельно от данных мира, чтобы будущий вайп его не затронул. ✅ Решение 0.3: профиль хранится локально на каждом сервере (как в Rust), без внешнего сервиса. Доступ к хранилищу — через отдельный интерфейс, чтобы при необходимости вынести профиль в общий сервис без переделки игрового кода.

### Р5. Онлайн-сервисы — ❓

Этап 1 — **OnlineSubsystemNull** (разработка, подключение по IP/LAN). Rust использует Steam (вход, браузер серверов). Выбор Steam / EOS зависит от площадки продаж — **вопрос к вам**. Код подключения пишется через абстракции Online Subsystem, смена сервиса не потребует переделки.

### Р6. Хостинг — ❓

В Rust есть официальные серверы и серверы сообщества (владельцы запускают серверный билд сами). Вопрос к вам: планируются ли серверы сообщества в ROXI. Не влияет на Этап 1.

### Р7. Античит — позже

Основа — авторитетность из Р1. Клиентский античит (EAC через EOS — бесплатно; Rust использует EAC) — ближе к релизу.

## 4. План Этапа 1

1. Базовые C++ классы: `ARoxiGameMode`, `ARoxiGameState`, `ARoxiPlayerState`, `ARoxiPlayerController`, доработка `ARoxiCharacter` (`TObjectPtr`, Push Model, своя лог-категория). Blueprint-наследники в `Content/Roxi/Core/`, пешка задаётся в Blueprint, а не строкой в C++.
2. Включение Push Model в конфигурации. Ограничение: в Launcher-движке Push Model скомпилирован только для Editor (`bWithPushModel` требует уникального окружения сборки). В PIE работает; в упакованном билде — после перехода на движок из исходников (`bWithPushModel = true` в Target.cs). Код пишется под Push Model уже сейчас.
3. Проверка: PIE / Listen Server с 2–4 клиентами — подключение и движение.
4. Нагрузочный стенд: N серверных ботов, двигающихся по карте; замеры (`stat net`, Unreal Insights). Затем — то же со включённой сеткой Replication Graph (Р2). На Listen Server цифры грубые; честный тест на 100 игроков — после сборки Dedicated Server.

Игровых механик на Этапе 1 нет — только сетевой фундамент.
